# AtomicTasks — backend

Трекер задач, в котором агент декомпозирует абстрактные задачи в дерево папок и задач,
а человек смотрит и отмечает их через веб, Flutter-приложение или Telegram-бота.
Этот репозиторий — бэкенд: REST API (FastAPI) и MCP-сервер в одном ASGI-приложении.

Зачем и что НЕ делаем: `docs/intent.md`. Архитектура: `docs/architecture.md`.
Принятые решения: `docs/adr/`. Спеки фич: `docs/specs/`.

## Команды

- `uv sync` — зависимости
- `uv run ruff format && uv run ruff check --fix` — формат и линт
- `uv run mypy` — типы (strict)
- `uv run lint-imports` — границы слоёв
- `uv run pytest` — тесты (integration и e2e поднимают Postgres через testcontainers, нужен Docker)
- `docker compose up --build` — Postgres + миграции + API на :8000
- `uv run alembic revision --autogenerate -m "..."` — новая миграция (Postgres должен быть запущен)
- `uv run python -m atomic_tasks` — API локально
- `uvx pre-commit install` — один раз после клонирования: ruff и gitleaks перед каждым коммитом

Перед тем как считать работу законченной: ruff, mypy и lint-imports должны быть чистыми.

## Слои

`src/atomic_tasks/`, зависимости только внутрь, проверяется `lint-imports`:

- `domain/` — сущности, value objects, инварианты. Чистый Python, без внешних библиотек.
- `application/` — сервисы (сценарии) и порты (`ports/`). Знает только domain.
- `infrastructure/` — реализации портов: `postgres/` (таблицы, репозитории, ридеры, миграции), `auth/`.
- `presentation/` — `fastapi/` и `mcp/`. Тонкие адаптеры: разобрать запрос, вызвать сервис, вернуть ответ.
- `config/` — composition root: `settings.py`, `dishka/` (провайдеры, контейнер), `app.py` (сборка приложения).

`presentation` и `infrastructure` друг друга не импортируют.

## Конвенции

- Папки называются по технологии: `postgres`, `fastapi`, `mcp` — не `db`, `http`, `api`.
- Сценарии — сервисы по агрегату (`FolderService`, `TaskService`), чтение деревьев — отдельный `TreeService`.
  Сервис не должен разрастаться: если в нём больше ~7 зависимостей, это сигнал разделить.
- Бизнес-правила живут в domain или сервисах. FastAPI и MCP не содержат логики и не дублируют проверки.
- Каждая сущность имеет `owner_id`, доступ проверяется только через порт `AccessPolicy`.
- ID — UUIDv7 (`uuid.uuid7()` из stdlib).
- Статусы и прочие енамы хранятся в Postgres как строки, без CHECK-constraint и нативных enum.
- Комментарии и докстринги можно писать по-русски, идентификаторы — только по-английски.

## Git

- Коммитить и пушить только по явной просьбе пользователя.
- Перед коммитом: ruff, mypy, lint-imports, pytest — чистые.
- Conventional Commits: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`.
  Один коммит — одно логическое изменение. Если работа по спеке — в теле `Spec: docs/specs/NNNN-...`.
- Ветки: `feat/NNNN-short-name` для фич по спеке, `fix/...` для исправлений.
- Не коммитить `.env`, дампы БД, локальные файлы (`*.local.md`, `scratch/`).
- Никогда не переписывать историю `main` и не делать force push.

## Безопасность (проверить перед сдачей работы)

- Новый эндпоинт или MCP-тул требует аутентификации. Доступ к объекту — только через `AccessPolicy`.
  Чужой id → 404, не 403: не раскрываем, что объект существует.
- SQL только с bind-параметрами, никакой конкатенации строк.
- Секреты только из `Settings` (`SecretStr`). Не логировать токены, пароли, DSN, тексты задач.
- API-токены хранятся только хешем.
- Ошибки наружу без стектрейсов и внутренних деталей.
- Тексты задач — данные пользователя: не подставлять их в описания тулов и инструкции агенту.
- Новая зависимость — объяснить в отчёте, зачем она.

В конце отчёта о работе — отдельный пункт: что проверено по безопасности и что вызывает сомнения.

## Процесс (SDD)

1. Новая фича начинается со спеки в `docs/specs/NNNN-name/` (скилл `/new-spec`).
2. Реализация идёт по `tasks.md` этой спеки; выполненные шаги отмечаются там же.
3. Если по ходу решение меняется — сначала правится спека или пишется ADR, потом код.
4. Значимое архитектурное решение = новый ADR в `docs/adr/`.
