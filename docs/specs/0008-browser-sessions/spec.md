# 0008. Сессии браузера: вход через бэкенд, httpOnly-cookie

Статус: черновик

Решение — ADR 0013. Потребитель — [atomic-tasks/web](https://github.com/atomic-tasks/web)
(ADR 0003 веба: сессия в cookie, сайт и API на одном хосте).

## Зачем

Веб-клиенту нужен вход, при котором токены не попадают в браузер. Два хоста:

- `WEB_HOST` (например `atomic.example.com`) — сайт; его `/api/` Traefik отдаёт бэкенду. Браузер видит
  один origin: cookie без CORS.
- `API_HOST` (например `api.atomic.example.com`) — бэкенд целиком для машинных клиентов: `/mcp`, `/docs`,
  `/openapi.json`, REST по Bearer. Сейчас бэкенд живёт на `atomic.example.com` — он переезжает.

Пользователь входит через Rauthy, бэкенд ставит httpOnly-cookie сессии на `WEB_HOST`, сайт узнаёт
пользователя через `GET /api/v1/me`.

## Сценарии

1. **Хосты** (выпускается отдельно, первым):
   - роутер `Host(WEB_HOST) && PathPrefix(/api/)` → сервис API (с тем же лимитом тела). Остальные пути
     `WEB_HOST` — сайту (его compose и роутер — в репозитории веба); до выкатки сайта — `404` от Traefik;
   - бэкенд переезжает на новый `API_HOST`: адрес ресурса MCP, разрешённые хосты, ресурс CIMD-клиентов
     в Rauthy, redirect URI Swagger, переменная `API_HOST` в GitHub. Коннекторы MCP переподключаются.
2. **Не вошёл.** Сайт вызывает `GET /api/v1/me` → `401` → показывает кнопку «Войти».
3. **Вход.** Кнопка ведёт браузер на `GET /api/v1/auth/login?return_to=/folders/123`. Бэкенд запоминает `state`,
   PKCE-verifier, `nonce` и `return_to` на время входа и перенаправляет в Rauthy. После входа Rauthy возвращает на
   `GET /api/v1/auth/callback`; бэкенд меняет code на токены, проверяет `id_token`, находит или создаёт
   пользователя (allowlist, `email_verified` — как в спеке 0001), создаёт сессию, ставит cookie и
   перенаправляет на `return_to`.
4. **Вход не удался** (не пустил allowlist, пользователь отключён, вход просрочен или подделан, ошибка Rauthy):
   редирект на `/?login_error=<код>`, коды — `access_denied`, `expired`, `failed`. Сайт показывает сообщение.
5. **Работа.** Запросы REST с cookie проходят так же, как с JWT, включая управление PAT.
6. **Выход.** `POST /api/v1/auth/logout` удаляет сессию, стирает cookie, отвечает `204` и
   `Clear-Site-Data: "cache", "storage"`. Без сессии — тоже `204`.
7. **Локальная разработка.** Сайт на `http://localhost:5173`, Vite проксирует `/api` в бэкенд — вход
   работает так же: redirect URI `http://localhost:5173/api/v1/auth/callback`. Без сайта — `WEB__ORIGIN`
   = `http://localhost:8000` и вход напрямую на `http://localhost:8000/api/v1/auth/login`.
8. **Вход только через хост сайта.** Redirect URI строится из `WEB__ORIGIN`, cookie `__Host-` привязаны
   к хосту: на `API_HOST` cookie-сессии нет by design, машинные клиенты работают только по Bearer.

## Правила и ограничения

**Сессия**
- Секрет — 32 случайных байта; в базе только SHA-256 (как у PAT). Строка: пользователь, создана, истекает
  (абсолютный предел), последняя активность.
- Срок — 30 дней с последней активности (продлевается не чаще раза в минуту), но не дольше 90 дней со входа.
- Отключённый пользователь (`disabled_at`) — 403, как для остальных способов входа.
- Токены Rauthy (access, refresh, id) после входа не хранятся.
- Просроченные сессии и попытки входа удаляются при следующем входе любого пользователя; отдельного cron нет.

**Временные данные входа**
- Строка в Postgres: `state` (в базе — хеш), PKCE-verifier, `nonce`, `return_to`, срок — 10 минут.
- В браузере — cookie `__Host-at_login` со значением `state`. На callback `state` из запроса должен совпасть
  с cookie, строка удаляется в той же операции, что и читается: второй раз вход не завершить.

**Cookie**
- `__Host-at_session` и `__Host-at_login`: `HttpOnly; Secure; SameSite=Lax; Path=/`, без `Domain`.
- `Secure` и на `http://localhost`: Chrome и Firefox принимают такие cookie на localhost, Safari — нет.

**Безопасность**
- `return_to` — только относительный путь: начинается с `/`, не с `//` и не с `/\`, без управляющих символов.
  Иначе — `/`.
- CSRF: для запросов, аутентифицированных cookie, методы кроме `GET`/`HEAD`/`OPTIONS` требуют `Origin`, равный
  origin сайта из настроек (прод — `https://WEB_HOST`, локально — `http://localhost:5173`). Иначе 403.
  Bearer-запросы не проверяются.
- `/mcp` cookie не принимает — только Bearer, как сейчас.
- Если в запросе есть и Bearer, и cookie — используется Bearer.
- В логах нет секретов сессии, `state`, verifier, кодов авторизации и токенов.

**API и конфигурация**
- Новые эндпоинты — со стабильными `operation_id` (`login`, `callback`, `logout`); cookie описана в OpenAPI
  как схема безопасности.
- В Rauthy — отдельный конфиденциальный клиент `atomic-tasks-web` (PKCE S256) с redirect URI прода и локальной
  разработки.
- Новые настройки (origin сайта, параметры клиента, сроки сессии) — через env, группа `WEB__`, по образцу
  `AuthSettings`. Без `WEB__ORIGIN` вход через браузер выключен: эндпоинты `/auth/*` отвечают `404`,
  cookie не принимается.
- Traefik: роутер API на `API_HOST` без изменений правила; новый роутер `/api/` на `WEB_HOST` — сценарий 1.
- Путей бэкенда на `WEB_HOST`, кроме `/api/`, нет: `/health`, `/docs`, `/mcp` — только на `API_HOST`.
  Доступность бэкенда сайт видит по ответу `GET /api/v1/me`.

## Вне рамок

- Деплой самого сайта (образ, его compose, роутер, релиз) — спека веба.
- Сохранение старого адреса бэкенда (`atomic.example.com/mcp` и т.п.) после переезда: он отдаётся сайту.
- Выход из сессии Rauthy (RP-initiated logout): после выхода повторный вход может пройти без пароля.
- Список сессий и выход на всех устройствах в интерфейсе.
- Несколько провайдеров на аккаунт (ADR 0009).
- CORS и вход с чужих доменов.
- Cookie-вход для `/mcp` и Swagger (`/docs` остаётся на JWT).

## Решения по открытым вопросам

- Сроки: 30 дней скользящий, 90 абсолютный.
- Временные данные входа — строка в БД, а не подписанная cookie: строгая одноразовость, без нового секрета.
- Хосты: сайт — `WEB_HOST` (`atomic.<domain>`) с `/api/` в бэкенд; бэкенд — `API_HOST` (`api.atomic.<domain>`).
  Отвергнуты: один хост с делёжкой путей (`/mcp` и `/.well-known` не спрятать под `/api`, сайт и бэкенд
  делят корень) и прямые запросы сайта на `API_HOST` (разные origin — CORS с credentials, против ADR 0013).
- Тесты: изоляция пользователей через cookie, CSRF-отказ, просроченная сессия, open redirect в `return_to`,
  повтор callback.
