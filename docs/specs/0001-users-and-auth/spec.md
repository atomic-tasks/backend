# 0001. Пользователи и аутентификация

Статус: согласована

## Зачем

Без пользователя нет `owner_id`, а без него нельзя ни хранить задачи, ни проверять изоляцию.
Нужен беспарольный вход через соцсети, один аккаунт на несколько соцсетей и доступ для агентов
(Claude Code, бот) по токену. Выбор IdP — ADR 0009 (Rauthy).

## Сценарии

1. **Первый вход.** Пользователь открывает `/docs`, жмёт Authorize, входит в Rauthy через Google или GitHub.
   Swagger получает JWT. При первом запросе к API бэкенд создаёт `users` и `user_identities`,
   если подтверждённый email есть в allowlist. Иначе — 403 с понятным текстом.
2. **Повторный вход.** Пользователь находится по `(issuer, sub)`. Email и имя обновляются из токена.
3. **Вход через одного провайдера.** Каждый пользователь входит через тот провайдер, с которым его аккаунт
   создан в Rauthy. Несколько провайдеров на один аккаунт Rauthy не поддерживает (ADR 0009).
4. **Профиль.** `GET /api/v1/me` возвращает id, имя, email.
5. **Создание токена.** `POST /api/v1/tokens` с названием, правами (`read` или `write`) и сроком
   (по умолчанию 90 дней, 1–365 или явно бессрочный). Токен показывается один раз.
6. **Список и отзыв.** `GET /api/v1/tokens` — без секретов: название, префикс, права, даты создания,
   последнего использования и окончания. `DELETE /api/v1/tokens/{id}` — отзыв.
7. **Claude Code.** `claude mcp add --transport http atomic-tasks <url>/mcp --header "Authorization: Bearer at_..."`.
   Запрос к `/mcp` с валидным токеном проходит, без токена или с невалидным — 401.

## Правила и ограничения

**Идентификация**
- Пользователь определяется только по `(issuer, sub)`. По email никогда не ищем.
- Allowlist (`AUTH__ALLOWED_EMAILS`) проверяется только при создании пользователя и требует `email_verified = true`.
  Пустой список — регистрация закрыта.
- Удаление из allowlist не блокирует существующего пользователя. Блокировка — `users.disabled_at`:
  отключённый пользователь получает 403 на всё, его токены не работают.

**JWT**
- Проверяются подпись (ключи из JWKS; EdDSA или RS256, симметричные алгоритмы запрещены), `iss`, `aud`, `exp`.
- JWKS кэшируется; при неизвестном `kid` ключи перечитываются один раз.

**Personal access tokens**
- Формат `at_<prefix>_<secret>`: prefix — 8 символов для узнавания в списке, secret — 32 случайных байта (base64url).
- Хранится только SHA-256 от всего токена.
- `write` включает `read`. Токен с `read` не может менять данные ни через REST, ни через MCP.
- Создавать, смотреть и отзывать токены можно только с JWT-сессией, не с PAT:
  утёкший токен не может выпустить себе новый.
- Просроченный или отозванный токен — 401. Не больше 10 активных токенов на пользователя.
- `last_used_at` обновляется не чаще раза в минуту.

**Доступ по умолчанию**
- Все эндпоинты, кроме `/health`, `/docs` и `/openapi.json`, требуют аутентификации.
- Пользователь видит и отзывает только свои токены. Чужой id — 404.
- 401 отдаётся с `WWW-Authenticate: Bearer`.

## Вне рамок

- Несколько провайдеров на один аккаунт — после переезда на Zitadel (ADR 0009).

- OAuth для коннектора в приложении Claude (DCR, protected resource metadata) — отдельная спека.
- Sign in with Apple — вместе с mobile.
- Веб-интерфейс токенов, привязка Telegram, удаление аккаунта и экспорт данных, админка пользователей.
- Rate limiting — отдельная спека, до открытия регистрации.
- Деплой Rauthy на сервер — в спеке деплоя.
