# 0006. Деплой: VPS, домены, HTTPS, Rauthy в проде

Статус: реализована

## Зачем

Боту (0008) и коннектору в приложении Claude (0007) нужен публичный HTTPS-адрес API и IdP.
Сейчас всё работает только на `localhost`: образ публикуется в ghcr (0005), но его некуда выкатывать.

## Сценарии

- **Первый запуск на сервере.** Автор по runbook `docs/deploy.md` готовит VPS: DNS-записи, пользователя для
  деплоя, каталог стека, `.env` с секретами. Затем запускает выкатку `v0.1.0`. После неё:
  - `https://<API_HOST>/health` отвечает `ok`, `/docs` открывается по HTTPS с валидным сертификатом;
  - `https://<AUTH_HOST>/auth/v1/` — Rauthy; автор входит в админку, заводит passkey, настраивает Google и GitHub
    с прод-redirect URI и клиента Swagger;
  - вход в Swagger через Google создаёт пользователя, `POST /api/v1/tokens` выдаёт PAT;
  - Claude Code подключается к `https://<API_HOST>/mcp` с этим PAT и видит дерево.
- **Выкатка релиза.** Автор пушит тег `vX.Y.Z` (как в 0005). После публикации образа и GitHub Release workflow
  ждёт подтверждения в environment `production`. Автор жмёт Approve, джоба выкатывает **ровно эту версию**:
  тянет образ, применяет миграции, перезапускает API и проверяет, что `/openapi.json` отдаёт новую версию.
  Если проверка не прошла — джоба красная.
- **Откат.** Автор запускает тот же workflow вручную (`workflow_dispatch`) с версией предыдущего релиза.
  Миграции назад не откатываются: откат возможен, только если новая схема БД совместима со старым кодом.
  Иначе — восстановление из бэкапа (runbook).
- **Бэкап.** Раз в сутки на сервере снимаются дампы обеих баз (`atomic_tasks` и `rauthy`). Хранятся 7 дней.
  Автор забирает свежий дамп на ноутбук одной командой из runbook и умеет восстановить из него стек.

## Правила и ограничения

- **Топология.** Один compose-проект на сервере: Postgres, Rauthy, миграции, API, как локально. Rauthy и API
  стоят за уже работающим на VPS **Traefik**: подключаются к его docker-сети, маршруты задаются labels.
  Свой reverse proxy не ставим.
- **Домены.** API — на `API_HOST` (например, `atomic.<домен>`), Rauthy — на `AUTH_HOST` (`auth.<домен>`).
  Issuer — `https://<AUTH_HOST>/auth/v1/`. У Rauthy отдельный хост, чтобы потом можно было вынести его
  на другой сервер для других сервисов: пока хост не меняется, `(issuer, sub)` в `user_identities` остаются
  валидными.
- **Ничего в репозитории о конкретном сервере.** Домены, имя сети Traefik, entrypoint, certresolver, адрес
  сервера — переменные: в `.env` на сервере и в переменных или секретах GitHub environment `production`.
  В репозитории — шаблоны и `.env.example` для прода.
- **Наружу только 443 через Traefik** (80 — только редирект на https, если так настроен Traefik). Порты Postgres,
  Rauthy и API на хост не публикуются.
- **HTTPS везде.** Сертификаты выдаёт Traefik. Rauthy в проде с безопасными cookies (без `danger-insecure`),
  в режиме за прокси с доверием только к сети Traefik. API доверяет `X-Forwarded-*` только от прокси.
- **Админка Rauthy с обязательной MFA** (`admin_force_mfa = true`) и passkey администратора. SMTP не настраиваем:
  без него письма (сброс пароля, OTP по почте) не работают — это осознанно.
- **Регистрация закрыта**, как локально: пользователи появляются только через Google или GitHub с auto-onboarding,
  доступ к данным ограничивает `AUTH__ALLOWED_EMAILS`.
- **Лимит тела запроса** на прокси — 1 МиБ для API (закрывает техдолг из roadmap).
- **MCP** принимает только `Host` = `API_HOST` (`MCP__ALLOWED_HOSTS`).
- **Выкатка — только опубликованный образ с точной версией** (`ghcr.io/atomic-tasks/backend:X.Y.Z`), не `latest`
  и не сборка на сервере. Пакет в ghcr публичный, на сервере `docker login` не нужен.
- **Порядок выкатки:** pull → миграции отдельным одноразовым контейнером → перезапуск API → проверка версии.
  Если миграции упали, API не перезапускается и продолжает работать на старой версии.
- **Доступ CI к серверу минимальный.** SSH-ключ деплоя лежит только в environment `production` с обязательным
  подтверждением автора. На сервере ключ ограничен forced command: им можно только запустить выкатку
  указанной версии, без shell. Хост сервера проверяется по закреплённому `known_hosts`.
- **Секреты** — в `.env` на сервере (права `600`, владелец — пользователь деплоя), в git их нет.
- **Бэкап:** `pg_dump -Fc` обеих баз раз в сутки (cron на хосте), каталог вне docker-томов, ротация 7 дней.
  Восстановление описано в runbook и проверено один раз на сервере.

## Вне рамок

- Внешнее хранилище бэкапов (S3, другой хост) — риск потери сервера принят, дамп забирается руками.
- SMTP для Rauthy, мониторинг, алерты, uptime-проверки, централизованные логи.
- Отдельный стек или отдельная БД для Rauthy: вынесем, когда он понадобится другим сервисам.
- Zero-downtime выкатка: перезапуск API даёт несколько секунд недоступности.
- Staging-окружение.
- Автоматический откат миграций.
- Rate limiting (до публичного запуска, см. roadmap).
- OAuth для коннектора Claude, DCR — спека 0007.

## Открытые вопросы

- ~~Как задаются параметры Rauthy 0.37 из env.~~ Все нужные — env: `PUB_URL`, `PROXY_MODE`, `TRUSTED_PROXIES`
  (через `\n`), `RP_ID`, `RP_ORIGIN` (с портом, даже `:443`), `COOKIE_MODE`; `admin_force_mfa` по умолчанию `true`.
  Прод-`config.toml` статичный, без подстановки. Важно: с `proxy_mode` Rauthy **блокирует запросы не из
  `trusted_proxies`**, поэтому туда входит и внутренняя сеть стека (фиксированная подсеть `INTERNAL_SUBNET`),
  из которой API забирает JWKS.
- ~~Issuer за прокси.~~ Проверено на проде (v0.2.0): с `scheme = "http"` и `proxy_mode` Rauthy отдаёт
  `https://<AUTH_HOST>/auth/v1/`, совпадает с `AUTH__ISSUER`.
- ~~Подсеть сети Traefik.~~ Берётся на сервере (`docs/deploy.md`, п. 1). Сеть внешняя, подсеть выбрана Docker
  автоматически: если сеть пересоздадут, `TRAEFIK_SUBNET` нужно обновить.
- ~~Память.~~ `docker stats` после первого запуска (VPS 2 ГБ, рядом другие сервисы): API ~124 МиБ,
  Rauthy ~100 МиБ (не 35–40, как заявлено авторами), Postgres ~87 МиБ — стек ~310 МиБ. Лимитов памяти пока нет.
- Вход через GitHub с приватным email — на проде не проверен, остаётся в техдолге roadmap.
- Первая выкатка из Actions упала на `.deploy.lock: Permission denied`: каталог стека был создан не под `deploy`.
  Runbook (п. 2) это уже предписывает; владелец каталога исправлен на сервере.
- Защита environment `production`: джоба `deploy` первого релиза создала его сама, **без правил** (GitHub так
  делает для несуществующего environment). Секретов ещё не было, выкатка не случилась. Правила выставлены
  после (reviewer, только `main` и `v*`), в runbook — «создать environment до первого тега».
