# 0009. Rauthy вместо Zitadel

Статус: принят, заменяет 0008

## Контекст
ADR 0008 выбрал Zitadel. На практике он занимает около 500 МБ памяти в простое, а текущий сервер этого не тянет.
При этом нужен полный сценарий уже сейчас: вход через соцсети, веб и мобильный клиент,
агент в приложении Claude на телефоне. Последнее требует полноценного OAuth-сервера с регистрацией клиентов:
коннекторы в приложении Claude не дают пользователю вставить личный токен (ввод заголовков — бета
для организаций, токен общий на всю организацию).

## Решение
- **Rauthy** (Rust, Apache-2.0) в том же `docker compose` на нашем Postgres. По заявлению авторов —
  около 35–40 МБ памяти. Есть вход через сторонних провайдеров, динамическая регистрация клиентов,
  passkeys, PKCE S256.
- Всё остальное из ADR 0008 без изменений: бэкенд — resource server, пользователь идентифицируется
  по `(issuer, sub)`, email не ключ, PAT для Claude Code, бота и скриптов.
- Алгоритм подписи JWT берётся из JWKS; допускаются EdDSA и RS256 (у Rauthy по умолчанию ed25519),
  симметричные алгоритмы запрещены.

## Альтернативы
- **Свой вход через Google на `authlib`** — легче всего по памяти, но не даёт OAuth-сервер для коннектора
  в приложении Claude, а эндпоинты входа и таблица сессий потом выбрасываются.
- **Zitadel** — зрелее и с большим сообществом, но по памяти не подходит текущему серверу.

## Известные ограничения (проверено локально)
- **Один внешний провайдер на аккаунт.** Аккаунт Rauthy связан максимум с одним провайдером, а email
  уникален. Поэтому «войти через Google или GitHub в один и тот же аккаунт» невозможно; склейка
  на стороне бэкенда не помогает, когда у человека один email в обоих провайдерах.
  Компромисс: один провайдер на человека — приемлемо, пока сервисом пользуются автор и коллеги.
- **Автосоздание пользователей** включается настройкой провайдера (auto-onboarding), а не открытой регистрацией.
  Открытая регистрация выключена; доступ к данным ограничивает allowlist бэкенда.

## Условие пересмотра
Перед открытием сервиса для всех — переезд на IdP с несколькими провайдерами на аккаунт (Zitadel, ADR 0008).
Данные не затрагиваются: связи «пользователь ↔ способы входа» хранятся у нас в `user_identities`.

## Последствия
- Сообщество у Rauthy заметно меньше. Вход через Google как сторонний провайдер и регистрацию клиента
  Claude проверяем первым же шагом спеки 0001; если не работает — пересматриваем решение.
- Смена IdP потом (на Zitadel или другой) не трогает данные: скрипт миграции создаёт пользователей в новом IdP
  через его API и записывает новые `(issuer, sub)` в `user_identities` тех же `users`;
  где перенос привязок соцсетей невозможен — одноразовый код привязки при первом входе.
  Клиенты один раз входят заново, коннектор Claude переподключается. PAT продолжают работать.
