# 0012. OAuth для MCP-коннектора: CIMD в Rauthy и токены, привязанные к ресурсу

Статус: принят

## Контекст
Коннекторы в приложении Claude подключаются к удалённому MCP-серверу только через OAuth по спецификации
MCP Authorization (ADR 0009). Клиент находит сервер авторизации через protected resource metadata
(RFC 9728), регистрирует себя одним из двух способов и запрашивает токен для конкретного ресурса (RFC 8707).

Способы регистрации:
- **DCR** (RFC 7591) — любой может зарегистрировать клиента со своими redirect URI. ADR 0008 допускал его
  только с rate limiting и доверенными redirect URI. Rauthy умеет ограничивать DCR по IP или общим токеном,
  но не по redirect URI. Зарегистрированные клиенты копятся в базе.
- **CIMD** (Client ID Metadata Document) — `client_id` это HTTPS-адрес JSON-документа на домене клиента.
  Сервер авторизации скачивает его при входе. В Rauthy это «ephemeral clients». В 0.37.2 они есть,
  и Rauthy объявляет `client_id_metadata_document_supported` (проверено, спека 0007).

У клиентов, регистрирующихся сами, `client_id` заранее неизвестен. Поэтому сверять `aud` со списком
наших client id, как для Swagger, нельзя.

## Решение
- **Регистрация — CIMD**: `ENABLE_EPHEMERAL_CLIENTS=true`. DCR остаётся выключенным.
- **Токен привязан к ресурсу.** Rauthy разрешает ephemeral-клиентам запрашивать только наш ресурс
  (`EPHEMERAL_CLIENTS_ALLOWED_RESOURCES` = публичный адрес `/mcp`). Бэкенд принимает JWT на `/mcp`,
  если в `aud` есть этот адрес (`MCP__RESOURCE_URL`) или один из наших client id (`AUTH__AUDIENCE`).
- **Токен ресурса MCP не принимается в REST** `/api/v1`. Бэкенд знает, куда пришёл запрос (`AuthTarget`),
  и выбирает допустимые `aud` в верификаторе, а не в адаптерах.
- Бэкенд отдаёт `/.well-known/oauth-protected-resource/mcp` и `WWW-Authenticate: Bearer resource_metadata=…`
  на `401`. Встроенную OAuth-поддержку SDK `mcp` не используем: аутентификация остаётся в одном `AuthService`.
- **Только доверенные клиенты.** Rauthy 0.37.2 при активной сессии выдаёт код ephemeral-клиенту без экрана
  согласия, а ограничить такие клиенты по домену не умеет. Поэтому токен, принятый по ресурсу MCP (в `aud` нет
  наших client id), бэкенд принимает, только если подписанный `azp` — `https`-адрес без порта на хосте из
  `MCP__TRUSTED_CLIENT_HOSTS` (по умолчанию `claude.ai`, `claude.com`). Документ на этих хостах может разместить
  только Anthropic. Проверка по хосту, а не по точному `client_id`: адрес документа коннектора Claude
  может меняться.
- Токен IdP, как и раньше, даёт права `write`. Доступ к данным ограничивает allowlist email.

## Альтернативы
- **DCR с лимитом по IP.** Работает с любым MCP-клиентом, но это открытая регистрация: любой может
  показывать пользователям страницу входа нашего Rauthy со своим redirect. Вернёмся к нему, если понадобятся
  клиенты без CIMD.
- **`default_aud` вместо `resource`.** Не подходит: у клиентов, регистрирующихся сами, нет настроек в админке,
  а MCP-клиент обязан отправлять `resource`.
- **Принимать любой токен нашего issuer.** Токен, выданный для чужого сервиса на том же Rauthy, работал бы у нас.

## Последствия
- Подключаются только MCP-клиенты с CIMD на доверенных хостах (Claude, Claude Code). Новый клиент — новый хост в настройке. Прочие — после включения DCR отдельным решением.
- Rauthy при каждом входе скачивает документ клиента: IdP ходит наружу по HTTPS (кэш — `EPHEMERAL_CLIENTS_CACHE_LIFETIME`).
- Включён `RFC_8252_ENABLE`: нативные клиенты (Claude Code) указывают loopback-redirect без порта, а слушают
  на случайном. Для loopback порт не сравнивается, для остальных redirect URI — строгое совпадение.
- Защита от переигрывания токена не зависит от того, как Rauthy проверяет `resource`: `aud` проверяет бэкенд.
- Смена IdP (ADR 0009) потребует, чтобы новый IdP поддерживал CIMD или DCR и RFC 8707.
