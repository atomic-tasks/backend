# 0008. Zitadel как IdP, personal access tokens для агентов

Статус: заменён 0009 (Zitadel слишком тяжёл для текущего сервера)

## Контекст
Нужен беспарольный вход через соцсети (Google, GitHub, позже Apple), несколько соцсетей на один аккаунт,
токены для web и mobile, OAuth-сервер для коннектора MCP в приложении Claude. Проект должен полностью
селфхоститься. Писать свой IdP — много кода, где любая ошибка становится уязвимостью.

## Решение
- **Zitadel** в том же `docker compose`, отдельная база `zitadel` на нашем Postgres.
  Соцсети, связки аккаунтов, сессии, выдача и обновление JWT — на стороне Zitadel.
- Бэкенд — resource server: проверяет JWT по JWKS из OIDC discovery, issuer задаётся настройкой.
- Пользователь идентифицируется только по `(issuer, sub)` из токена (`user_identities`). Email — для отображения
  и allowlist, никогда не ключ.
- **Personal access tokens** (`at_...`) для Claude Code, бота и скриптов; хранится только хеш.
- OAuth для коннектора в приложении Claude — позже, через DCR в Zitadel (Claude откатывается на DCR,
  если сервер не объявляет CIMD).

## Альтернативы
- **Keycloak** — уже поддерживает CIMD (экспериментально), но Java, тяжелее и сложнее в администрировании.
- **authentik** — DCR появился недавно, CIMD нет.
- **Свой вход через `authlib`** — просто для веба, но для mobile, нескольких соцсетей и OAuth-сервера для MCP
  по сути означает написать свой IdP.

## Последствия
- Ещё один сервис в compose, который надо обновлять и бэкапить (его база — в том же Postgres).
- Смена IdP возможна: новые `(issuer, sub)` привязываются к тем же `users`.
- Для коннектора в Claude понадобится включить DCR с открытой регистрацией клиентов — только с rate limiting
  и доверенными redirect URI.
